# @phoenix-ai/knowledge-graph

**Module:** Knowledge Graph & Provenance Store
**FRD reference:** see `docs/requirements/FRD.docx`, module section for "Knowledge Graph & Provenance Store"

## Responsibility

The single source of truth from which all OKF outputs are projected; stores every element with provenance.

## Status — Phase 2 (Canonical Knowledge Model) + P6-04 (Work Item model) + P6-05 (Reconciliation model) + P6-05 (Reconciliation model)

`src/` defines the canonical knowledge model (P2-01), its domain-neutral ontology foundation
(P2-02), the Architecture model (P2-03), the Domain/Entity model (P2-04), the
Persona/Journey/State model (P2-05), the Integration/API model (P2-06), the provenance model
(P2-07), the confidence model (P2-08), the evidence/reference model (P2-09), and the finalized OKF
YAML schema (P2-10) — a source-aware shape that future extraction/inference sources will produce
and future OKF renderers / graph storage will consume. All four domain areas planned for Phase 2,
all three cross-cutting metadata models, and the OKF serialization are now complete:

- `CanonicalKnowledgeObject<TAttributes>`, `CanonicalKnowledgeRelationship`,
  `CanonicalKnowledgeBundle`, plus `identity`/`evidence`/`validation` support types (P2-01).
- `StructuralCategory`/`RelationshipCategory`/`LifecycleState` (`ontology.ts`, P2-02) — the
  small, closed, universal classification every domain-specific `kind` value falls under.
- `SystemObject`/`ContainerObject`/`ComponentObject`/`ArchitectureRelationship`
  (`architecture.ts`, P2-03) — the first domain-specific `kind` vocabulary, typed on top of the
  generic envelope.
- `DomainObject`/`EntityObject`/`AggregateObject`/`EntityStateObject`/`DomainRelationship`
  (`domain.ts`, P2-04) — the second domain-specific `kind` vocabulary, following the same pattern.
- `PersonaObject`/`JourneyObject`/`FlowObject`/`ActionObject`/`JourneyRelationship`
  (`journey.ts`, P2-05) — the third domain-specific `kind` vocabulary; extends (does not
  redefine) P2-04's `EntityStateObject` via a new `triggersTransition` relationship.
- `ApiObject`/`InterfaceObject`/`IntegrationObject`/`DataFlowObject`/`IntegrationRelationship`
  (`integration.ts`, P2-06) — the fourth and last domain-specific `kind` vocabulary; reuses
  Phase 1's exact `IntegrationDirection` union for `IntegrationAttributes.interactionType`.
- `Source`/`validateSource`/`validateSources`/`validateSourceReferences` (`provenance.ts`, P2-07)
  — a resolvable, bundle-level registry for origin artifacts that `Provenance[]`/`Evidence[]`
  entries can reference by `sourceId`, plus stricter per-entry validation of `Provenance` itself
  (reused as-is from `@phoenix-ai/shared`, not redefined). Cross-cutting, not a fifth domain area.
- `ConfidenceBasis`/`ConfidenceCalculation`/`ConfidenceDetail` (`confidence.ts`, P2-08) — the
  FACT/DIRECTLY-OBSERVED vs DERIVED/INFERRED distinction, orthogonal to confidence _strength_
  (`Confidence.level`/`score`, `@phoenix-ai/shared`, untouched), added as an optional
  `confidenceDetail` sibling field on `CanonicalKnowledgeObject`/`CanonicalKnowledgeRelationship`.
  Structurally independent from `provenance.ts`'s `Source` by design. Cross-cutting, not a sixth
  domain area.
- `Evidence` (`evidence.ts`, P2-01/P2-09) — concrete supporting material for a claim (`id`,
  `sourceId`, `excerpt?`, `locator?`, plus P2-09's new `capturedAt?`/`sourceVersion?`); now also
  an optional field on `CanonicalKnowledgeRelationship` (previously object-only), with per-entry
  shape validation folded into the base validators. Distinguished from provenance ("where did this
  come from") and connected to, but structurally independent of, confidence.
- `OkfDocument`/`toOkfDocument`/`serializeOkfYaml`/`parseOkfYaml`/`parseAndValidateOkfYaml`/
  `validateOkfDocument` (`okf.ts`, P2-10) — the finalized, deterministic, versionable YAML
  serialization of `CanonicalKnowledgeBundle` (not a competing model): `OkfDocument` narrows
  `CanonicalKnowledgeBundle.okfVersion` from optional to required; validation delegates entirely
  to the existing bundle/source-reference validators. The contract Phase 3 connectors and a future
  `okf-renderers` implementation will target — see `docs/okf/README.md`.
- **`samples/aurora-commerce.sample.okf.yaml`** (P2-11) — a representative, hand-authored (not
  extracted) sample OKF document covering every concept P2-01 through P2-09 defined, validated
  against the real `validateOkfDocument`. Generated by `samples/generate-sample.ts` — a dev
  utility and worked template for future connectors, not part of this package's runtime API. See
  `docs/okf/sample.md`.
- **P2-12 — UI compatibility validation** (no new code — a validation exercise): confirms the
  canonical model/OKF schema can represent every field the six Phase 1 UI areas actually render,
  for Architecture/Domain/Integrations/System-identity; confirms Deployment/NFR and
  Review/Gaps/Drift have zero canonical representation (a pre-existing, now-proven condition, not
  fixed here). See `docs/okf/ui-validation.md`.
- `WorkItemObject`/`WorkItemRelationship` (`workitem.ts`, P6-04) — the fifth domain-specific `kind`
  vocabulary, `kind: 'workitem.issue'`, representing a ticket-tracker issue (Jira today, via
  `packages/ingestion-connectors`' P6-02 connector) as a domain-neutral canonical object. ONE object
  kind covers every tracker issue type (Epic/Story/Bug/Task/Sub-task/custom) — the tracker's own type
  name lands verbatim in `attributes.issueType` rather than becoming a separate `kind`, since a
  tracker's type taxonomy is project-configurable. `contains`/`relatesTo` (both REUSED from
  `domain.ts`, not new) represent parent/child issue hierarchy and cross-issue links respectively,
  with the tracker's real link-type name and direction preserved in relationship `attributes`.
- `ConflictObject` (`reconciliation.ts`, P6-05) — the sixth domain-specific `kind` vocabulary,
  `kind: 'reconciliation.conflict'`, and the FIRST to use `category: 'observation'` — the structural
  category P2-02 reserved for "a meta-statement ABOUT other knowledge objects" but that no real kind
  had filled until now (`tests/ui-coverage.test.ts` documented the gap since P2-12). Retains EVERY
  distinct value multiple sources claimed about the same subject/attribute, each with every source
  behind it — `packages/reconciliation-engine`'s job to build, this file's job only to shape.

calculation engine, any persistence layer, and any real extraction source. Phase 3's P3-01 defined

`packages/ingestion-connectors/README.md` and `docs/architecture/adr/0013-source-connector-contract.md`
— but no real connector exists yet, and nothing in this package changed for it. `okf.ts`'s own runtime
API still has no file-system I/O — the one place this package touches disk is
`samples/generate-sample.ts`, an opt-in dev script, not the package's build or runtime path.
`apps/api` declares a dependency on this package but does not import from it yet — Phase 1's API
areas remain on their own independent contracts in `packages/shared/src/contracts.ts`.

`workitem.ts` (P6-04) is model-only, matching every other domain file's own precedent: no Jira client,
no fact-to-canonical mapping (that is `packages/extraction-engine`'s `jira-bridge.ts`), no workflow/
status-transition inference over a Work Item's `attributes.status` (a single-snapshot fact, not a
history — see ADR 0028 "Limitations"), and no UI rendering (`apps/web`'s graph explorer is unaware of
`workitem.issue`).

`reconciliation.ts` (P6-05) is likewise model-only: no claim comparison, no confidence computation, no
source-type weighting (all `packages/reconciliation-engine`'s job). It does not add the FRD's full
`status: extracted|inferred|conflicted|human-confirmed` field to every canonical object/relationship
— a `ConflictObject` records a dispute as its own object rather than stamping the disputed objects
themselves; see ADR 0029 "Limitations".
